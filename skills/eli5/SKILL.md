# eli5 — 고치기 전에 그림으로 이해하기

앤트로픽 공식 `eli5`(Thariq Shihipar, MIT)는 지시문이 두 문장이다 — "전혀 모르는 사람에게 설명하듯, 큰 그림과 적은 글로 HTML을 만들어라." 이 스킬은 거기에 **조사 · 근거 표시 · 검증** 세 가지를 더한 판이다.

왜 더하는가: 정돈된 상자와 화살표는 설명이 정확하다는 인상을 준다. 하지만 그림의 사실성은 **무엇을 읽고 그렸는지**에만 달려 있다. 공식판에는 조사 지시도 검증 절차도 없다.

이름은 eli5지만 쓰임은 쉬운 설명이 아니다. **구현 전에 사람과 에이전트가 같은 시스템을 보고 있는지 확인하는 것**이다.

## 인자

```
/rakis:eli5 <설명할 대상> [--out <path>] [--quick]
```

- `--out` — 출력 경로. 기본은 CWD의 `eli5-{slug}.html` (slug는 대상을 영문 kebab-case 3~5단어로 축약)
- `--quick` — Phase 2 의미 검증 생략. 훑어보기 전용이며, **구현·리뷰의 근거로 쓰지 않는다.** 출력 상단에 `<!-- unverified -->` 주석과 배지를 남긴다

## 원칙

- 코드 실행 순서가 아니라 **사람과 시스템이 주고받는 일의 순서**로 그린다
- 단일 HTML 파일 — 외부 빌드·CDN 없이 브라우저에서 바로 열린다. "한 장"은 한 화면이 아니라 **파일 하나**라는 뜻이므로 스크롤은 허용
- **모르는 것은 그리지 않는다.** 빈칸으로 남기고 "확인 못 한 것"에 넣는다
- 문단이 길어지면 그림이 실패한 것이다. 글은 상자 라벨 수준으로

## Phase 0: 조사 — 그림보다 먼저

읽지 않은 것은 그리지 않는다.

1. 진입점 → 호출 경로 → 데이터 저장소 → 오류·롤백 경로 순으로 추적한다
2. 코드만으로 "왜"가 확정되지 않으면 근거 자료를 함께 읽는다 — ADR, `docs/`, 이슈·PR 본문, `git log -p --follow <file>`
3. **조사 기록표**를 만든다. Phase 2가 이 표로 검증하므로 생략하면 검증이 성립하지 않는다

| 그림 요소 | 근거 | 등급 |
|---|---|---|
| `AuthService → SessionStore` 화살표 | `src/auth/service.ts:88` | 확인 |
| "재시도 3회" | PR #412 본문 | 해석 |
| 결제 실패 시 큐 우회 | — | 미확인 |

- **확인** — 코드에서 직접 읽은 것
- **해석** — 기록(PR·이슈·커밋 메시지)을 근거로 한 추론
- **미확인** — 근거 없음. 설계 의도와 장애 원인이 여기 몰린다

대상이 코드가 아니면(개념·프로토콜·외부 서비스) 조사 대상을 소스 문서로 바꾸되 **근거 열은 그대로 채운다.**

## Phase 1: HTML 생성

- 인라인 SVG로 상자와 화살표. 상자가 겹치거나 화살표가 상자를 관통하지 않게 배치
- **3등급을 색으로 구분한다.** 색은 반드시 CSS 클래스로 — 인라인 색상은 테마 전환에 반응하지 않는다

```html
<style>
  :root { --fact: #1a7f37; --interp: #9a6700; --unknown: #82071e; }
  @media (prefers-color-scheme: dark) {
    :root { --fact: #3fb950; --interp: #d29922; --unknown: #f85149; }
  }
  .fact    { stroke: var(--fact);    color: var(--fact); }
  .interp  { stroke: var(--interp);  color: var(--interp);  stroke-dasharray: 4 3; }
  .unknown { stroke: var(--unknown); color: var(--unknown); stroke-dasharray: 2 4; }
</style>
```

- 모든 주장에 근거를 붙인다 — `src/auth/service.ts:88` 형태로 상자 아래 작은 글씨
- 기술 스택·정책 상세는 그림 안이 아니라 **하단 요약 카드**로 뺀다
- 마지막 섹션은 **"확인 못 한 것"** — Phase 0의 미확인 행을 그대로 옮긴다. 이게 다음 조사 목록이 된다

## Phase 2: 검증 — 두 종류다, 하나만 하면 실패

### 구조·렌더링

실제로 브라우저에서 연다. 잘림 · 겹침 · 화살표 관통 · 읽을 수 없는 작은 글자를 확인한다.

- Chrome 자동화가 있으면 `mcp__claude-in-chrome__*`로 열어 스크린샷까지 확인
- 없으면 `open "{out}"` 실행 후 사용자에게 확인을 요청한다. **"열릴 것이다"로 넘어가지 않는다**

### 의미

조사 기록표의 모든 행을 그림과 대조한다.

- 근거 열이 빈 요소 → **미확인 등급으로 강등**하거나 삭제
- 그림에는 있는데 표에 없는 요소 → **지어낸 것이다. 삭제한다**
- 표에는 있는데 그림에 없는 요소 → 누락인지 의도적 생략인지 판단해 기록

`--quick`이면 이 절을 건너뛰되, 건너뛰었다는 사실을 출력과 HTML 양쪽에 남긴다.

## Phase 3: 출력

```
✓ eli5-{slug}.html
  조사: {N}개 파일 · {M}개 기록
  근거: 확인 {a} · 해석 {b} · 미확인 {c}
  확인 못 한 것:
    - {항목}
```

마지막 줄로 안내한다:

> 이 HTML은 코드를 대신하지 않는다. 어디부터 어떤 관점으로 읽을지 정해주는 첫 지도다. 중요한 결론은 원본 코드·로그·변경 이력으로 다시 확인한다.

## 하지 않는 것

- 보안 검토·장애 원인 보고서를 대체하지 않는다
- 그림이 틀렸다는 지적을 받기 전에 구현으로 넘어가지 않는다 — 이 스킬의 존재 이유가 그 확인 단계다
- 조사 없이 그림부터 그리지 않는다. 그리는 시간보다 **잘못 이해한 채 구현을 시작하는 비용**이 크다
